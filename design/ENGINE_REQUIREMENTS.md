# Engine requirements

Requirements for the engine: loading a world, building each thing's current version, play, saves and the writer. Owned by thwarter coder. RFC 2119 keywords are used as in `REQUIREMENTS.md`, and every requirement answers to its principles. The content rules the engine implements are in `design/CONTENT_REQUIREMENTS.md`; the engine rules settled during the states design are REQ-ENG-10 to 29 below.

Split out of `REQUIREMENTS.md` on 2026-11-23. The REQ-ENG ids are stable. A change another component needs here goes to the commander as a message.

## Requirements

- REQ-ENG-1: `WorldEngine` MUST own the location graph (`WorldGraph`) and MUST be able to load an entire world directory in one pass, per REQ-CF-7's error-collection requirement.
- REQ-ENG-2: `WorldEngine` MUST be able to report every location whose `connections` target an unloaded location `id` (this backs REQ-CLI-3).
- REQ-ENG-3: `CharacterEngine` MUST own loaded character definitions and their live state (current location, mood, health) separately from the static `Character` data parsed from content files, so that a character's runtime state can change during a session without mutating the authored definition.
- REQ-ENG-4: `NarrativeEngine` MUST be able to register plot points and narrative arcs and check a plot point's prerequisites against a set of completed plot points before allowing it to trigger.
- REQ-ENG-5: `GameEngine` MUST orchestrate the other three engines and dispatch player actions (at minimum: move, take, look, examine) to per-action-type handlers.
- REQ-ENG-6: Object placement and lookup (which world entity owns "does object X exist, and where is it") is the World Engine's responsibility, per REQ-ENG-1; there is no separate Object Engine, since objects don't have enough independent behavior to justify one.
- REQ-ENG-7: The engine MUST be able to write an entity back to its file. Changing one field MUST leave every other part of the file as it was: field order, comments, fields the engine doesn't model (REQ-CF-6) and the body. Full editing (REQ-CON-6) MAY replace a file's whole text, but only after the new text parses. A file that names a template (`inherits:`) MAY take required keys from it, so the writer MUST check such a file only for sound frontmatter, `id` and `type`, and leave typing it with its template to the engine, which reports any problem (REQ-ENG-8). Changing an entity's `id` or `type` is refused until renaming is specified, since either moves the file. The writer MUST refuse to edit an `id` defined in more than one file. A new entity MUST be written in the format of `design/CONTENT_FORMAT.md`, at the path that document gives for its type, and MUST refuse any path that resolves outside the world directory (an `id` containing `..`, for example).
- REQ-ENG-8: The engine MUST be able to change the loaded world in memory (add, change or remove an entity or an exit) and report the problems `validate` would find after that change, without reloading the world from disk.
- REQ-ENG-9: The engine's interface to the console MUST offer at least: a description of a location (title, body, exits with whether each target exists, characters, objects with whether each has a card); the play state (REQ-ENG-23); and an action result (the text to show, and what changed). The coder and console coder agree its Rust shape between them and record it in `design/ARCHITECTURE.md`.


### Loading (`design/STATES.md` › Files)

- REQ-ENG-10: The loader MUST decide what a file is from where it sits, never from its contents: a folder holding `index.md` is one thing (a bundle) whose other files are its states, and whose `chapters/` folder holds its chapter overlays; `_index.md` marks an area; in any `chapters/` folder a numbered file defines a chapter in that scope and an unnumbered one is an overlay (REQ-ENG-14); files in `world/` define the world (REQ-CF-20); everything else is a one-file thing. State and overlay files MUST NOT set `id`, `type` or `state:`; a layer that does is kept with those keys removed and reported, so one bad key doesn't cause more errors.
- REQ-ENG-11: A bundle MUST be a leaf: it MAY hold state files, one `chapters/` folder and a `templates/` folder, and nothing else. A nested `index.md` is an error. `index`, `_index`, `chapters` and `templates` MUST NOT be state names.
- REQ-ENG-12: A thing's `id` MUST come from its one file or its `index.md`; the folder is only how the loader finds the files. A bundle whose `id` doesn't match its folder MUST be warned about.
- REQ-ENG-13: The loader MUST skip other tools' files (REQ-CF-24), and MUST NOT walk into a skipped folder. Only the part of a path inside the world counts, so a world kept under a dot folder still loads. The engine MUST say, for any file it read, what that file is (a thing, a state, an overlay, a chapter, an area, a `world/` file, a template, or a problem with its reason), so the console needn't guess.

### Chapters

- REQ-ENG-14: A chapter MUST be identified by its scope (the folder whose `chapters/` defines it) and its name without the number, so names need only be unique within a scope. A chapter name in an overlay, a `chapter:` action or a version request MUST be looked up from the referring thing's folder outward to the root. A scoped definition that hides an outer chapter of the same name MUST be warned about. Mixing numbered and unnumbered parts in one chapter path, and an unnumbered file in the root `chapters/`, are errors. A sub-chapter's folder MUST have an `_index.md`.

### Building a version (`design/STATES.md` › What applies, Inheritance)

- REQ-ENG-15: A thing's version MUST be built on request from its layers, in order: overlays from the folders above it (outermost first), its templates (most distant first), its `index.md`, its current state, then its own chapter overlays; within each level a parent chapter comes before its sub-chapter. Siblings never apply.
- REQ-ENG-16: Layers MUST merge as raw YAML before the result is typed: maps merge key by key all the way down, scalars and lists replace, and `null` removes an inherited key. Every key MUST remember the file it came from. A replaced list and a removed key MUST be warned about.
- REQ-ENG-17: Prose MUST merge by part: a layer's description replaces the description below it only if something is left once author comments are removed. Keyword sections (REQ-ENG-35) are never part of a layer's description. A folder's overlay adds its description after each thing's instead of replacing it.
- REQ-ENG-18: Only `index.md` MAY set `state:`, which names the starting state; a bundle MAY leave it out, and then `index.md` alone is the version until something switches it. The world tables MUST hold each thing's starting version (starting state, no chapter), and `validate` MUST check every state against every chapter visible from the thing.
- REQ-ENG-19: A template MUST be found by path from the world root, or by bare name in `templates/` folders from the thing's scope outward, then among the built-ins (REQ-CF-21). A template MUST NOT pass down its `id` or `template:`. A template bundle MUST pass down its states: the thing has the template's states plus its own, a state file of its own with the same name is layered over the template's, and the template's `state:` is the thing's starting state unless the thing names one. A name that finds nothing, a loop, and a chain more than 4 deep are problems.
- REQ-ENG-20: Wherever frontmatter takes an id, a name that isn't an id MUST be resolved as the thing whose file it names, by path from the root or by a file name only one file has (REQ-CF-25). A file name more than one file has MUST be reported as ambiguous, naming the files.

### Ids and values

- REQ-ENG-21: `game`, `story`, `player`, `location` and `this` MUST NOT be ids, and ids MUST NOT contain a dot. An id used by two kinds MUST be warned about, since bare references can't tell them apart.
- REQ-ENG-22: Values MUST be strings. Variables (REQ-CF-16) MUST read a value set in play first, then the declared starting value, and for a thing the value in its current version. An undeclared variable, and an undeclared value an action's `sets:` names, MUST be warned about, and play MUST show an unknown variable as blank. `requires:` MUST stay limited to `has:` until a real case needs more.

### Play and saves

- REQ-ENG-23: `PlayState` MUST keep the current location, the inventory, what was taken from each room, each thing's state only when it differs from its starting state, the current chapter, values by full name, visits per room, the turn count (one per player action the game understood) and the faint things found. Play MUST show each thing in its current version, and a room MUST NOT list what the player carries.
- REQ-ENG-24: An object's named action MUST check `requires:`, then apply `becomes:`, `sets:` and `chapter:`, and reply with a built-in reply made from the verb and the object's name, until reply sections are built (`design/SECTIONS.md`). States and chapters MAY go back as well as forward, and moving to a chapter applies only it and its parents.
- REQ-ENG-25: Play MUST honour `visibility:` (REQ-CF-18) for objects, characters and exits: faint things appear once found by searching or examining the room, hidden ones answer only to an action that names them exactly, and absent ones can't be named.
- REQ-ENG-26: When a noun matches several things, the reply MUST be the `## When: #ambiguous` section of the nearest template they share, else a built-in reply in the story's voice, varied, which a story MAY replace.
- REQ-ENG-27: Saves MUST be versioned (`thwarter_save: 2`) and MUST load older versions. On load, a state that no longer exists MUST fall back to the starting state, a thing that's gone MUST be dropped, and a chapter that's gone MUST fall back to the nearest earlier one in its scope, each with a warning.

### Writing bundles

- REQ-ENG-28: Turning a one-file thing into a bundle MUST write the new files first and rename the old file to `index.md` last, so a half-done move leaves a duplicate `id` that `validate` reports, never a silent loss.
- REQ-ENG-29: A bundle MUST save through one call that checks the merged thing before writing anything, writes only the files whose text changed (each to a temporary file, checked, then renamed), and reports exactly which files were written if a rename fails. Renaming or deleting a state MUST be a command, and a rename MUST update every `becomes:` and `state:` that names it.
- REQ-ENG-30: Renaming a thing's `id` MUST move its file, or its bundle folder with everything in it, to the path the new id gives (for a room, the id is the path, so moving a room into an area is a rename), and MUST update every reference to the old id: exits, `characters:`, `objects:`, `inventory`, `default_location`, `world/index.md`'s `start:`, and links and variables in prose, in the style each was written (a link stays a link). Every edit MUST be checked in memory before anything is written, and the rename MUST be refused if the new path or id is taken, or the new id is reserved. References inside an action's `becomes:` and `requires: { has: }` MUST be rewritten too, and checked by reading the file back as exactly what was expected; one that can't be rewritten that safely MUST be left as it is and reported for the author to fix. The report MUST list every file moved and written, and the engine MUST take the same change.
- REQ-ENG-50: Removing a thing (`/remove`, Bruce, 2026-11-24) MUST delete its file, or its bundle folder with everything in it, and take every reference to its id out, found as REQ-ENG-30 finds them: it leaves every `objects:`, `characters:` and `inventory` list; an exit into a removed room or through a removed door goes; a door with a removed room on one side goes too, with its other side's exit; and a `default_location` naming a removed room is cleared. Scenery with no card loses only its list entries. A room that still holds people or things, and the world's start room, MUST be refused with what to do first. Prose links, an action's `becomes:` or `requires:`, and a door's `key` MUST be left as written and reported for the author. `WorldWriter::plan_remove` MUST say what will be deleted and changed, writing nothing, so the console can ask first; `remove_loaded` MUST do exactly that, all of it checked in memory before anything is written. No undo yet.
- REQ-ENG-31: A door (REQ-CF-19) MUST be its own kind of thing. A room's exit that names a door MUST lead to the room the door's other side names, or for a portal, the side's `to:`; play MUST refuse an exit through a door that isn't `passable:` in its current state, show each door's current text by the room's exits, and, for a `transparent:` door, a line about the room beyond. A door MAY have actions, as an object does. `validate` MUST report a door with no sides, a plain door with more than two, every door built-in (`door`, `portal`, `locked-door`) MUST open and close as it comes, and `validate` MUST warn about a door with one side so far (half-built, as `/add door bedroom` leaves it, leading nowhere until its other room is added), a portal side without `to:` when the portal has more than two, a side that isn't a room, and an exit through a door the room isn't a side of, and MUST warn about a side whose direction differs from the room's exit and a side whose room has no exit through the door.

### Player commands

- REQ-ENG-32: The engine MUST parse a player's typed line into an action or a reply through one call every client uses, `GameEngine::parse_command(&WorldEngine, line, &PlayState) -> Parsed` (`Action`, a `Reply` asking for a noun, or `Unknown`), carrying the verbs, aliases, articles and directions of `design/PLAYER_COMMANDS.md` (REQ-PC-1 to 8). Any other verb with a noun MUST become `PlayAction::Use`, an object's named action (REQ-PC-13), and the built-in verbs MUST be read first, so an object action named like one never shadows it (REQ-PC-15). A reply or an unknown line MUST NOT reach `act`, so it counts no turn.
- REQ-ENG-33: A verb no object or door has as an action, in any state or chapter, MUST be unknown when its noun names nothing the player can see or carries, including the room (REQ-PC-14); with a noun that names something, it MUST reach `act`, which replies that the player can't.
- REQ-ENG-34: The engine MUST own where games are saved, so every client stores them the same way (REQ-PC-18, REQ-CFG-6): `engines::saves` gives each world's save folder under `settings::state_dir`, the file for a save name (letters, digits, `-` and `_` only, so a save can't land outside its folder), the saves there by name, and `save_named` and `load_named`. A working copy's saves MUST be keyed by its folder name and a stable hash of its full path, and an installed world's by its persona and world, so reinstalling keeps them.

### Sections

- REQ-ENG-35: The loader MUST read keyword sections (`design/SECTIONS.md`): a `##` heading starting `When:` or `Unless:` followed by `#tags` opens one, which runs to the next `#` or `##` heading, and headings in fenced code don't count. A ` ```thwarter ` block first in a section MUST be read as that section's data, as YAML with frontmatter's limits; one anywhere else, and `id`, `type` or `state` in one, MUST be warned about. A heading word that isn't a `#tag`, a block that doesn't parse and an unclosed block are problems. Sections MUST NOT create states, and `<!-- -->` MUST be only a comment, never shown to a player. `#ambiguous` and `#searched` are reserved for engine moments (REQ-ENG-26). A section MUST match when all its tags (`When:`) or none of them (`Unless:`) are in the turn's set.
- REQ-ENG-36: Each turn MUST have a set of tags (`design/SECTIONS.md`): `@` for each thing the player holds and for the room, `#` for the chapter and its parents, and `#` for the current state of the thing being described. A thing's description MUST be its prose followed by each of its sections (its templates' first) that matches that set. On an action's turn the set also holds `#<verb>`, `@<target>` and `@<what it's used with>` (`hit window with stick`); the reply MUST be every `When:` section naming `#<verb>` that matches, in the target, then what's used, then the room, matched after the action against its outcome (REQ-ENG-39). With a matching frontmatter action, the action's mechanics apply and a reply section replaces the built-in reply (a refusal stays built in); without one, a reply section is the whole action and changes nothing, and with neither the reply MUST be "Nothing happens." A `#verb` in any heading MUST count as a verb the world knows (REQ-PC-14). The room's `## When: #searched` section MUST lead the reply to searching. A door that isn't passable MUST answer `go` with its matching `## When: #go` section, else a built-in reply. Tags on other things' states and on values are not built (Bruce to decide).
- REQ-ENG-37: Play MUST show each `@id` in prose as that thing's name in the version play sees, and an `@` that names nothing as the bare word, which `validate` MUST warn about. An `@` that follows a letter, digit or dot, or sits in inline code, is not a mention. The parser MUST drop `to` or `at` straight after a verb other than `go` and `look` (REQ-PC-20), and `go` MUST try its whole phrase as an exit, then the phrase without `to` and an article.

### Scripts and outcomes

- REQ-ENG-38: A thing MAY have a Rhai script (`design/SECTIONS.md` › Scripts): its bundle's `actions.rhai`, or one ```rhai block in its file, kept out of the description; both is a problem, and so is a script that doesn't compile, naming the file. Each two-argument function is an action named by its verb (`attempt-open` is `attempt_open`), called with the thing and the turn as read-only maps: the thing's `id`, `title`, `state`, values and `held`, and the turn's `verb` and `used` (the `with` thing, or `()`). It MUST return `become("state")`, a reason, nothing (`no-action`) or a list of `become`, `keep` and `change`. A template's script MUST pass down, and a thing's own function MUST replace a template's of the same name. A thing's own script for a verb runs instead of a frontmatter action of that name, and a frontmatter action runs instead of a template's script. Scripts MUST run sandboxed: no files, network, modules, `eval` or printing, and a cap of 100,000 operations, with call depth, expression depth and sizes capped too; an error is an author note and the outcome `no-action`.
- REQ-ENG-39: Each action turn MUST have one outcome: the state the target moved into, else the reason the script returned, else `no-action`; a built-in verb's outcome is the target's current state. In a reply, a `#` tag that names a state of the target MUST mean the state it ended up in, an action tag that is also a state means ending up in it unless the section names an outcome, and a reply in a state file that names no outcome MUST mean "ended up here". Other `#` tags match the outcome or the chapter. A thing's own reply MUST replace its template's or a built-in's for the same action and outcome. With no reply, an action that ran gets a built-in reply and one that didn't gets "Nothing happens." `take`'s turn MUST look for a `## When: #take` reply, which replaces the built-in one.
- REQ-ENG-40: `keep(turn.used)` MUST move what the action was used with, from the player or the room, into the thing (`PlayState.held`, saved), where the player can name and examine it and gets it back with `take`. Only the used thing can be kept. The built-in `locked-door` MUST be the bundle `design/STATES.md` › Keys shows, with `vars: { key: "" }` meaning no key is needed, and `validate` MUST warn about a `key` that names nothing.
- REQ-ENG-41: A script MAY change another thing with `change("id", "state")` only when either one lists the other in frontmatter `connects:`; otherwise it's an author note and nothing changes. `validate` MUST warn about a `connects:` entry that names nothing. Mentions in prose don't connect (Bruce to decide).

### Things inside things

- REQ-ENG-42: An object's `objects:` MUST list what it holds, read and layered like a location's (REQ-CF-31). `WorldEngine::placement(id)` MUST give every room, character and object that lists a thing, in the starting versions; more than one is a `validate` warning, except for scenery, which may stand in several rooms. An object that holds itself through what it holds is a problem. In play, what an object holds MUST be in scope whenever the object is, however deep, with a cycle followed once; the room view MUST list every visible thing by title, each held thing right after its holder in the holder's `holds:` word (`on` by default, `in`, or any word: `Old photo (on the walls)`, `Coins (in the chest)`), and an empty `holds:` is a `validate` warning. Edit mode's room view MUST list held things too, each under its holder, from the authored lists; examining a holder MUST show its description and then what it holds (`You see: …`, made in one place while Bruce chooses its form). What a thing keeps in play (`keep()`, REQ-ENG-40) is the same relation: taking from an authored holder is recorded as taken from it, and taking from a thing that kept it removes it from `held`, so saves stay as they were (REQ-ENG-27).

### Play text

- REQ-ENG-43: Play MUST word rooms and the inventory in plain sentences for a player (Bruce, 2026-11-23 and 2026-11-24), each line a template a world MAY change in `world.toml`'s `[play]` table (`engines::play_text`). A room reads, in order: its name only if `show_room_names` (off by default); its description, with who's here on the next line ("Captain Marcus is here."); after a blank line, what's here ("You see a chair, a bed, and an old shirt.", names lowercased with `a`, `an` or `some`, scenery left out since the prose describes it) and what those things hold, grouped by holder ("There's an old photo on the walls and some coins in the chest."); then, after a blank line, the ways out, naming each door ("You can go north, east, or down through an open iron door."). A door's own text shows when it's examined, not on every look, and an examined holder says what it holds the room's way. The inventory reads "You have a key.". A key `[play]` doesn't know, or a value of the wrong kind, is a warning. What an author needs (directions with targets, ids, notes) belongs in the console's sidebar, not in play text. The test world's `world.toml` holds every setting at its default, as the reference.
- REQ-ENG-45: Built-in replies MUST read as the story, never as the system: an ambiguous noun asks one plain question ("Which key do you want to take, the brass key or the iron key?", "Who do you want to examine, King Aldric or Queen Aldric?"); a closed door named by direction says which and how ("The iron door is locked."); a person can't be talked to with no reply written ("The cook has nothing to say."); one-paragraph replies from several things run together as one paragraph; and a line play can't read quotes it in plain quotation marks, not code marks (`I don't understand "xyzzy".`).
- REQ-ENG-46: `validate` MUST warn about a character whose `default_location` room doesn't list it in `characters:`, since play shows only who a room lists.
- REQ-ENG-47: `engines::door_id(from_room, to_room, direction)` MUST give the id for a new door joining two rooms, the same in every client (Bruce, 2026-11-24): `door-<from>-<to>-<direction>`, lowercased, with an area's `/` and anything else not a letter or digit as one `-`, so it's a safe file name (`door-house-attic-house-landing-down`).
- REQ-ENG-48: The loader MUST read each `questions/<name>.md` as a question set (REQ-CF-32), never as a thing, and `WorldEngine::questions_for_thing(folder, id, template, kind)` MUST give the whole set to ask for a new thing made in `folder`: the set named for its id, else its template's, else its kind's, each the nearest from `folder` out to the world's root, then the built-in (`engines::questions`). A set named for nothing yet is fine. `validate` MUST report a file there without `type: questions`, and warn about an option whose construct isn't `set`, `recipe`, `ask thing` or `ask value`, and more than one `(default)` under a question.
- REQ-ENG-49: Every sentence thwarter writes MUST come from a text table (`design/ENGINE_TEXT.md`): `engines::texts::Texts` holds `[play]`, `[engine]` and `[console]`, each with compiled-in defaults in `src/builtins/text/`, and answers `text(table, key, &args)`. A value is text, a list of texts picked by `turn % len` (never at random), or a setting's true or false. Overrides (`world.toml`'s `[play]` and `[engine]`, the personal config's `[console]`) MUST warn about a key the defaults don't have and a value of the wrong kind.

### Forgiving verbs

Play's verbs forgive the way console commands do (REQ-CON-56; Bruce, 2026-11-24). Proposed; not built.

- REQ-ENG-51: Verb aliases MUST live in a table, not the parser: compiled-in defaults in `src/builtins/verbs.toml` (`[verbs]`, `alias = "verb"`: `get = "take"`, `x = "examine"`, `l = "look"`, `i = "inventory"`, and the rest REQ-PC-6 lists today), with a world's `world.toml` `[verbs]` over them. A world MAY alias its own object verbs (`yank = "pull"`). It's a separate table from `[engine]` because its keys are open-ended, so an unknown key isn't a warning. `validate` MUST warn about an alias whose verb nothing knows, and about an alias that is a direction, a direction's shorthand, or a built-in verb.
- REQ-ENG-52: A typed verb MUST resolve in this order, the first match winning: a direction or its shorthand (`n`, `s`, `e`, `w`, `ne`, `u`, `d`, `in`, `out`); a built-in verb; an alias; a verb a world thing answers to (REQ-PC-13); then a unique prefix of at least two letters among the built-in verbs and the verbs a thing in scope answers to. A prefix MUST NOT beat any exact match, so `in` is always a direction and `l` always `look`. A prefix that fits several verbs MUST ask, not guess: the `[engine]` key `which_verb` ("Do you mean {or}?", outcome `#ambiguous-verb`), and the turn doesn't count.
- REQ-ENG-53: A verb that matches nothing but is one small typo from a candidate in REQ-ENG-52's last step, or from an alias (one letter added, missing, swapped or changed), MUST get the `[engine]` key `did_you_mean` (`Did you mean "{verb}"?`, outcome `#not-understood #suggest`), naming every such verb with `{or}`, instead of `not_understood` (REQ-PC-24). It's a suggestion only: it MUST NOT run the guess, and the turn doesn't count.
- REQ-ENG-54: Prefixes and suggestions MUST apply to verbs only, not nouns. Nouns already match loosely (REQ-PC-9), and suggesting a noun could name a hidden or faint thing the player hasn't found. For the same reason, a world verb is a prefix or suggestion candidate only when a thing in scope answers to it.

### Checking a world

- REQ-ENG-44: `WorldEngine::validation(strict)` MUST give what `thwart validate` reports for the world as it is now, in-memory changes included: its problems, which fail it, its warnings, which don't, and one summary line. Every client that checks a world (`thwart validate`, the console's `/validate`) MUST use it, so their results never differ (Bruce, 2026-11-24).

Requirements REQ-ENG-4 and REQ-ENG-5 describe required capability, not required completeness: an engine satisfying "MUST be able to dispatch player actions" needs a dispatch mechanism, but nothing here requires every action's *effects* to be implemented. Current status against every requirement in this section is tracked in `design/ARCHITECTURE.md`'s implementation status table, not duplicated here, so status and specification don't drift apart again (see `design/DECISIONS.md` for why that drift happened once already).
